## History 

Coroutines in Python have evolved significantly over time, becoming a fundamental part of the language's concurrency model. The journey began with simple generators, moved through dedicated syntax, and culminated in the modern, user-friendly `async/await` keywords.

### Generators as Coroutines

The earliest form of coroutines in Python were **generators**. Starting with **PEP 342** in Python 2.5, generators were enhanced with the `.send()`, `.throw()`, and `.close()` methods. This allowed a generator to not only **yield** values but also **receive** data, enabling it to pause its execution and be controlled externally. This gave birth to the concept of coroutines using a **generator-based syntax**, where a function could both produce a sequence of values and act as a concurrent task.

***

### The Rise of `yield from`

While generator-based coroutines were powerful, they were also somewhat confusing. The syntax for delegating control from one generator to another was clunky. **PEP 380**, introduced in Python 3.3, addressed this with the **`yield from`** expression. This syntax provided a cleaner way to **delegate** to a subgenerator, making it easier to chain coroutines together and write more complex asynchronous code. However, this was still a bit of a workaround; the core concept of a coroutine was still tied to the generator protocol, not a dedicated feature.

***

### The `async/await` Revolution

The biggest leap came with **PEP 492** in Python 3.5, which introduced the dedicated **`async` and `await`** syntax. This was a game-changer for several reasons:

* **Clarity and Intent**: The `async` keyword clearly marks a function as a coroutine, and `await` explicitly indicates a suspension point where the program yields control to the event loop. This makes the code's intent much clearer.
* **Separation of Concerns**: This new syntax formally separated coroutines from generators. A function defined with `async def` is an `async` function, not just a fancy generator. This allowed Python to optimize coroutine behavior independently of generators.
* **Widespread Adoption**: The intuitive nature of `async/await` led to the rapid development of the **`asyncio` library** and a thriving ecosystem of third-party asynchronous libraries for everything from web servers to database clients.

In subsequent versions of Python, the old `yield from` syntax for coroutines was officially **deprecated** and eventually **removed**, solidifying `async/await` as the standard and only way to write coroutines.

The history of coroutines in Python is a story of gradual refinement, moving from a clever but limited hack to a first-class language feature that is now central to modern concurrent programming in Python.

## Concepts

Let's break down these key concepts in `asyncio`.

### Semaphore & Bounded Semaphore 🚦
A **semaphore** is a synchronization primitive used to limit the number of coroutines that can access a shared resource at the same time. Think of it as a gatekeeper with a limited number of "passes." A coroutine must acquire a pass to proceed and releases it when it's done. If all passes are taken, other coroutines will be blocked until one is released. This is crucial for controlling concurrency, like preventing an API from being overwhelmed with too many simultaneous requests.

A **semaphore** is a synchronization tool that controls access to a shared resource by a limited number of concurrent tasks, but it doesn't prevent a task from releasing the semaphore more times than it acquired it. A **bounded semaphore**, on the other hand, is a specific type of semaphore that raises an error if a task tries to release it more times than it has been acquired, thus ensuring proper usage.


#### Semaphore 🚦

A regular semaphore, as implemented in `asyncio.Semaphore`, is like a simple counter. When a task calls `acquire()`, the counter decreases. When a task calls `release()`, the counter increases. The key difference is that the `release()` operation can increment the counter **indefinitely**, even if the count is already at its initial value. This can lead to a state where the semaphore count becomes corrupted, potentially allowing more tasks to acquire it than intended.


#### Bounded Semaphore 🔒

A bounded semaphore, found in libraries like `threading.BoundedSemaphore` and similarly in `asyncio` patterns, adds a safety check. It tracks the initial number of permits it was created with and ensures the count **never exceeds this initial value**. If a task tries to call `release()` and the count is already at its maximum, it raises a `ValueError` or a similar exception. This prevents programming errors where a semaphore is released by a task that didn't acquire it or is released too many times. 

***

### Event Loop 🔄
The **event loop** is the central orchestrator of `asyncio`. It's a single-threaded entity that manages and schedules all asynchronous tasks. It constantly runs in a loop, picking tasks that are ready to execute and running them until they pause (e.g., at an `await` statement). When a task pauses to wait for an I/O operation (like a network request), the event loop immediately switches to another task that is ready to run. This is what makes `asyncio` non-blocking and highly efficient for I/O-bound operations. 

Can there be more thn 1 event loop in a single threaded program?

No, a single-threaded program can only have **one running event loop at a time**. The event loop is a core concept of `asyncio` that manages and schedules all asynchronous tasks on that single thread.


**How the Event Loop Works**

The event loop is essentially a `while` loop that continuously checks for tasks that are ready to run. It's the central hub for concurrency in a single-threaded environment. Having more than one event loop would be contradictory to this design, as there would be no way for them to hand off control to each other on the same thread without one of them being paused.

However, a program can **create multiple event loops** and run them one after another. You could start one loop, run some tasks, close it, and then create and run another one. But you cannot have them both active simultaneously.

For example:

```python
import asyncio

async def my_coroutine():
    print("Running a task.")

# Create and run the first event loop
loop1 = asyncio.new_event_loop()
loop1.run_until_complete(my_coroutine())
loop1.close()

# Create and run the second event loop
loop2 = asyncio.
new_event_loop()
loop2.run_until_complete(my_coroutine())
loop2.close()
```

While this code works, it doesn't demonstrate concurrency. The second loop only begins after the first one has finished and been closed. The true power of `asyncio` is in having **a single loop manage many tasks** concurrently.

***

### Task 📝
A **task** is a coroutine that has been scheduled to run on the event loop. When you wrap a coroutine with `asyncio.create_task()` or `asyncio.ensure_future()`, you are creating a Task object. This object represents the independent execution of your coroutine. The event loop then takes this task and adds it to its queue of things to run. The Task is what allows a coroutine to run in the background, concurrently with other tasks.

***

### Future 🔮
A **future** is an object that represents a result that may not yet be available. It's a low-level object that serves as a placeholder for a result that will be computed later. You don't typically create Future objects directly; instead, you interact with `Tasks`, which are a higher-level implementation of a Future. The main purpose of a Future is to act as a bridge between the asynchronous world and the value that will eventually be computed. When a coroutine needs a result that is not yet ready, it can `await` the Future object. Once the result is set on the Future, any coroutines awaiting it are unblocked and can resume their execution.

## Chaining asyncio.run()

If you chain multiple `asyncio.run()` calls, each one will **create a new event loop**, run its coroutine to completion, and then shut down the loop.

This is not a common pattern and generally isn't what you want for concurrent operations. The purpose of `asyncio` is to run multiple tasks **within a single event loop** to achieve concurrency. Chaining `asyncio.run()` calls effectively makes your program sequential; the second call won't begin until the first one has completely finished and its event loop has been closed.

### 📝 Example of Chained Calls

Consider this code:

```python
import asyncio
import time

async def task(name, sleep_time):
    print(f"Task {name} starting, will sleep for {sleep_time} seconds.")
    await asyncio.sleep(sleep_time)
    print(f"Task {name} finished.")

async def main1():
    await asyncio.gather(task("A", 2), task("B", 1))

async def main2():
    await task("C", 3)

start_time = time.time()
asyncio.run(main1())
print("-" * 20)
asyncio.run(main2())
end_time = time.time()
print(f"Total execution time: {end_time - start_time:.2f} seconds")
```

The output would show that "main1" takes approximately 2 seconds (the longest task), and then "main2" takes another 3 seconds. The total execution time will be around 5 seconds, not 3 seconds. The two `asyncio.run()` calls are entirely isolated and sequential.

### ⚠️ A Better Approach

For true concurrency, you should wrap all your tasks within a single top-level `async` function and call `asyncio.run()` just once.

```python
import asyncio
import time

async def task(name, sleep_time):
    print(f"Task {name} starting, will sleep for {sleep_time} seconds.")
    await asyncio.sleep(sleep_time)
    print(f"Task {name} finished.")

async def combined_main():
    await asyncio.gather(
        task("A", 2), 
        task("B", 1),
        task("C", 3)
    )

start_time = time.time()
asyncio.run(combined_main())
end_time = time.time()
print(f"Total execution time: {end_time - start_time:.2f} seconds")
```

In this case, all three tasks run concurrently on the same event loop. The total execution time will be approximately 3 seconds, as `asyncio.gather()` waits for the longest-running task to complete.

The key takeaway is to use `asyncio.run()` as a single entry point for your entire asynchronous program to leverage the power of a single event loop.
