## Concurrency vs Parallelism

- In concurrency the execution is not necessarily happening at the same time. There is progress being made but that does not mean there is work happening. e.g. Operating system where it makes progress on serveral tasks. Essentially, each task gets a slice of cpu to execute and move forward. 
- In parallelism, multiple executions ARE happening at the same time! Usually, the emphasis is on incresing throughput and optimizing resource i.e. hardware usage. E.g. 3D rendering, data analysis. 


## I/O bound and CPU bound tasks

- If a program is CPU bound, we can increase the number of processors and structure our program to spawn multiple threads that run individually on a dedicated or shared CPU. Here, ofcourse - we can also only use parallelisation. 
- Similarly, if a task is I/O bound, it makes sense to give up CPU while we are waiting on the I/O operation to complete. 

## Deadlocks, Liveness and Reentrant Locks

- Multi-threaded applicaitons are sharing the resources, which leads to these common follies. 
- Deadlock: 2 or more threads aren't able to make progress bc resource help by T1 depends on T2 and vice versa. 
- Liveness: Deadlock program has lost it's livenes. 
- Live-lock: 2 threads are reacting in response to one another and neither is making progress due to a deadlock. 
- Starvation: Application is unable to get any CPU time or access to shared resource. The other "greedy" threads continue hogging. 
- Reentraint lock: If a thread already holds the lock, and is trying to acquire it, then it is allowed. This is not the case with normal locks, they will result in a deadlock instead. 

E.g. code that can lead to deadlock-
```c
void increment(){
 
  acquire MUTEX_A
  acquire MUTEX_B
    // do work here
  release MUTEX_B
  release MUTEX_A
    
}


void decrement(){
  
  acquire MUTEX_B
  acquire MUTEX_A
    // do work here
  release MUTEX_A
  release MUTEX_B
    
}
```

## Mutex vs Semaphore

- Mutex: Can be acquired only by a single thread. It is used to control access to shared resouce | critical section. e.g. shared datastructure. 
- Semaphore: Limit access to a collection of resources. e.g. database connection pools. Semaphores can also be used for signaling among threads. e.g. producer increments to signal that there is data, and consumer decrements to signal that it has consumed. 
- A mutex is "owned" by the thread that has acquired it, but with sempahores there is no such concept. 

## Mutex vs Monitor

### The Meta
- Monitors are language level constructs, including Python. It is a mutex along with some conditional signals. 
- Usually, multi-threaded applications acquire and release lock by waiting on a conditional-
```c
void busy_wait_function() {
    // acquire mutex
    while (predicate is false) {
      // release mutex
      // acquire mutex
    }
    // do something useful
    // release mutex
}
```
- Now, if we wanted to ensure that the predicate value doesn't change, we would want to acquire a lock before evaluating the predicate ( as above ). If we also wanted to wait until the predicate satifie our condition, we'd want to wait on it. 
- Conceptually, each condition variable exposes 2 methdos - `wait()` and `signal()`. 
  - `wait()`: causes the associated mutex to be atomically released, and the calling thread would be placed in the wait queue. Since the mutex is now released, it can be acquired by other threads. 
  - `signal()`: Once, the producer has produced, it wants to let the consumer know, here it then  updates the conditional, which causes the threads in the wait queue to move to ready queue, and become ready for execution. The producer then releases the mutex by actually calling signal and the thread in the ready queue starts executing post acquiring the mutex. 
```c
void efficient_waiting_function() {
    mutex.acquire()
    while (predicate == false) {
      cond_var.wait()
    }
    // Do something useful
    mutex.release()     
}

void change_predicate() {
    mutex.acquire()
    set predicate = true
    cond_var.signal()
    mutex.release()
}
```
Running through this example- 
1. Thread A: `efficient_waiting_function()` --> mutex acquired --> `predicate = false`  --> enters the loop --> `cond_var.wait()` --> mutex released --> wait queue
2. Thread B: `change_predicate()` --> mutex acquired --> set `predicte = true` --> `cond_var.signal()` --> Thread A into ready queue --> `mutex.release()` 
3. Thread A starts execution

Note - the `while()` loop, is because we want to ensure that the value of predicate doesn't change between executions. Exxentially, after being singaled, we want to re-check the predicate before we enter into the critical section. You break the loop becuase predicate is true, you enter critical section - execute and then release the lock. 


### Finally, monitors

Okay, now we get into what is a monitor.
It is a mutex + conditions
OR
An entity with 2 queues to place the threads (entry queue , wait queue )

1. When a thread A enters a monitor it is placed into the entry set. 
2. If no other threads owns the monitor, which is equivalent to saying no thread is actively executing within the monitor section, then thread A will acquire monitor and is said to own it too. 
3. Thread A will continue to execture within the monitor section till it exits the monitor call or calls `wait()` on an associated condition variable, and he is hence placed into the wait set. 
4. While thread A owns the monitor, no other thread will be able to execute any critical section protected by the monitor. 
5. New threads claiming ownership of the monitor are placed into the entry queue. 
6. Now, if thread A is on the wait set, and thread B comes along -- it is first placed in the entry set, and then it acquires the monitor and continues execution. 
7. If thread B exits the monitor section without calling `notify()` on the conditional, then thread A will remain in the wait set! 
8. Thread B can also invoke `wait()` and be placed in the wait set along with A.
9. Eventually, some thread must come along and call `notify()`. 
10. Essentially, it helps achieve **mutual exlusion AND cooperation**. 

### Mesa vs Hoare Monitors

So far, what we discussed above are what Mesa monitors work like. 
In Hoare monitors, the signaling thread B yields the monitor to the woken up thread A and thread A enters the monitor while thread B sits out. 
This guaranteees that the predicate will not have changed, and instead of checking for the predicate in a loop, and if/else clause would suffice. 

Mesa monitors are more efficient than Hoare monitors. 

## Semaphore vs Monitor

- A monitor and a semaphore are interchangeable. Theoretically, one can be constructed out of the other or one can be reduced to the other. However, monitors take care of atomically acquiring the necessary locks whereas, with semaphores, the onus of appropriately acquiring and releasing locks is on the developer, which can be error-prone.
- Semaphores are lightweight when compared to monitors, which are bloated. However, the tendency to misuse semaphores is far greater than monitors. When using a semaphore and mutex pair as an alternative to a monitor, it is easy to lock the wrong mutex or just forget to lock altogether. Even though both constructs can be used to solve the same problem, monitors provide a pre-packaged solution with less dependency on a developer's skill to get the locking right.
- A semaphore can allow several threads access to a given resource or critical section. However, only a single thread can own the monitor and access associated resource at any point.
- Semaphores can be used to address the issue of missed signals. However, with monitors, the additional state, called the predicate, needs to be maintained apart from the condition variable and the mutex, which make up the monitor, to solve the issue of missed signals.

## GIL 

- Python is an interpreted language, hence it uses an interpreter, a program that executes other programs. 
- At a higher level, when we run a .py file, the python interpreter compiles the source code into byte code. The generated byte code is a lower-level platform-independent representation that can be understood by the PVM. 
- In the next step, the byte code is routed to the PVM for execution. This then executes the code line by line. (PVM is part of the interpretor)

- The Python Inerpretor can only execute 1 thread at a time! This is because of the way CPython was implemented. This design has a direct consequences on the performance of CPU bound programs since they don't experience any speed-up in the presence of additional processors. 

### Why was Python designed to run on a single core? 

- The answer lies in how memory management works in Python. 
- In Python, a reference count is associated with each object in a program. If an object has 0 reference count, the object is deallocated. 
- Now, to avoid race condition for this reference count per object -
  - There could be a lock per object : but slow, can lead to deadlocks
  - Hence, a compromise was made which wa to have a single lock that provides access to the python interpretor. i.e. the GIL.
- Execution of Python bytecode requires access to the GIL. 

### Little deep dive

[GIL code](https://github.com/python/cpython/blob/3.7/Python/ceval_gil.h)
Notes about the implementation:
- The GIL is just a boolean variable (locked) whose access is protected
    by a mutex (gil_mutex), and whose changes are signalled by a condition
    variable (gil_cond). gil_mutex is taken for short periods of time,
    and therefore mostly uncontended.
- In the GIL-holding thread, the main loop (PyEval_EvalFrameEx) must be
    able to release the GIL on demand by another thread. A volatile boolean
    variable (gil_drop_request) is used for that purpose, which is checked
    at every turn of the eval loop. That variable is set after a wait of
    `interval` microseconds on `gil_cond` has timed out.
    [Actually, another volatile boolean variable (eval_breaker) is used
    which ORs several conditions into one. Volatile booleans are
    sufficient as inter-thread signalling means since Python is run
    on cache-coherent architectures only.]
- A thread wanting to take the GIL will first let pass a given amount of
    time (`interval` microseconds) before setting gil_drop_request. This
    encourages a defined switching period, but doesn't enforce it since
    opcodes can take an arbitrary time to execute.
    The `interval` value is available for the user to read and modify
    using the Python API `sys.{get,set}switchinterval()`.
- When a thread releases the GIL and gil_drop_request is set, that thread
    ensures that another GIL-awaiting thread gets scheduled.
    It does so by waiting on a condition variable (switch_cond) until
    the value of last_holder is changed to something else than its
    own thread state pointer, indicating that another thread was able to
    take the GIL.
    This is meant to prohibit the latency-adverse behaviour on multi-core
    machines where one thread would speculatively release the GIL, but still
    run and end up being the first to re-acquire it, making the "timeslices"
    much longer than expected.
    (Note: this mechanism is enabled with FORCE_SWITCHING above)

## Amdahl's Law

The law specifies teh maximum speedup that can be achieved when parallelizing the execution of a program. 
```
    S(n) =     1
            ------
            (1-P) + P/n
```
S(n) = speedup achieved by using n cores.
P = fraction of program that is parallelizable.
1-P = fraction of program that must be executed serially.

As N approaches infinite, you can imagine what the equation looks like. 

## Moore's Law

Gordon Moore -- co-founder of Intel, observed the number of transistors that can be packed into a given unit of space doubles every *2* years, and in turn the porcessing power of computers doubles, and the cost halves. 

Initially, the clock speeds of processors also doubled along with the transistor count. This is because as transistors get smaller, their frequency increases and propagation delays decrease because now the transistors are packed closer together. However, the promise of exponential growth by Moore’s law came to an end more than a decade ago with respect to clock speeds.

In 10 years from 2000 to 2009, clock speed just increased from 1.3 GHz to 2.8 GHz merely doubling in a decade rather than increasing 32 times as expected by Moore's law.
